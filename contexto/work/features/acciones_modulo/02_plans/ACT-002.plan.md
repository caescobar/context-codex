### A1. Repo Standards (Backend)
- FastEndpoints activo con `AddFastEndpoints`/`UseFastEndpoints` y rutas `api/v1`.
- Patrón endpoint consistente: `Tags(...)`, `Policies(PermissionClaims.*)`, `req.Adapt<...>()`, `Send.OkAsync`/`Send.ErrorsAsync`.
- CQRS-lite vigente: `ICommand<Result<T>>` + `ICommandHandler<,>` para commands/queries.
- `Result<T>` es envelope común de éxito/error.
- Estructura `Features/<Area>/<Action>/` estable para nuevos endpoints de historia.

### A2. Repo Standards (DB)
- Fuente dominante de schema para este requirement: `telemetric-api/scripts/*.sql` (decisión explícita).
- Entidades de Acciones ya están en `IApplicationDbContext` y mapeadas en `TelemetricDbContext`.
- Naming SQL observado en singular PascalCase con PK/FK/índices explícitos.
- Soft-delete/auditoría (`IsDeleted`, `CreatedAt`, `UpdatedAt`) y filtros (`HasQueryFilter`) ya aplican en módulo.
- Unicidad de `RuleInstance` (`DeviceId`, `RuleTemplateVersionId`) ya definida en EF y SQL.

### A3. Story Fit Check
- ACT-002 pide runtime anti-spam (auto-reset, latch, cooldown) y rehidratación por `RuleCheckpoint`.
- Hay base reusable: cola/routing `telemetry.actions` y publicación `actions` ya presentes en KISS.
- `ActionAttempt` y `RuleCheckpoint` existen como modelo persistente para trazabilidad/checkpoint.
- Gap de implementación (esperable): falta engine de evaluación de reglas y contrato endpoint real de `Resolve manual` en API.
- No hay contradicción activa entre storypack, spec y decisiones para ejecutar plan de implementación.

### A4. Guardrails Confirmation
